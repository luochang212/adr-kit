# 项目复盘：v0.1.0 → v0.24.0 — 2026-10-22

> 范围：2026-08-16 首个提交至 v0.24.0（2026-10-22），33 个版本、298 个提交、
> 30 条决策记录。方法：逐版本比对 git 历史、CHANGELOG、`adr/` 全部记录
> （含 Deliberation 附录与 supersede 链）及 `docs/reviews/` 两轮全仓评审。
> 动因：大量决策由 agent 主导落地，维护者需要对项目演进建立完整认知。
> 本文只记整体结论；逐版本的"背景 / 决定 / 做了什么 / 回头看"见随附报告。

## 一句话结论

项目走的是"快速迭代 + 诚实记录 + 及时拆除"：错得不少，但几乎每个失误都在
1–4 周内被发现并处理（dogfood、全仓评审、实地反馈、supersede 自审），
且每次更替都留下了可追溯的理由。最危险的错误是把错误机制养成长期
遗产，这个错误一次也没犯：封印、环境推断、双载体都拆干净了。

## 做对了什么

1. **尽早 dogfood（0.9.0，ADR 2）。** 本仓库用 adr/ 管理自己：格式破坏变成
   自伤、每次破坏性变更都伴随自我迁移、30 条记录成为最好的测试集。这是
   全部正确决策的放大器。front matter 布局自那以后再未破坏性变更，
   而 0.9.0 之前的"最终设计"平均寿命不到两周。
2. **决策记录本身的质量。** Provenance 双轴显式声明（raised-by /
   decided-by，不推断）、Alternatives 如实记录被拒选项与理由、supersede 链
   完整。今天能复盘"当时为什么"，完全依赖这些记录。工具在它自己身上
   兑现了承诺。
3. **删除的勇气与速度。** `--json`、前向兼容代码、decided-by 推断、
   CLAUDE.md 双载体、归档封印：发现不对就整体拆除，"deleted, not
   deprecated"，不留僵尸表面。
4. **唯一依赖的纪律。** 运行时依赖始终只有 `yaml`；CLI 解析用
   `node:util` 的 parseArgs；生成的 HTML 零 CDN 自包含。克制贯穿 33 个
   版本没有松动。
5. **校验失败即成功信号 + 双侧测试。** 新提案在填完前就该校验失败；每条
   规则同时测"过的过、不过的因正确原因不过"。测试行数（约 8,000）超过
   源码（约 7,200）。
6. **评审与反馈回路。** 两轮全仓评审（报告与复现脚本公开入库）、真实使用
   现场的 field findings 回流（jev-unsloth）、MIT 上游 pin + CI 硬门禁。
   错了能被发现，且发现过程留痕。
7. **前提失效就更新决策。** Claude Code 原生支持 AGENTS.md 后撤掉双载体
   （ADR 24）；"无用户"前提过期后把兼容立场改写为公开发布的产品契约
   （ADR 28）。每条都先核实事实、预埋重评触发条件。

## 做错了什么

1. **decided-by 环境推断（0.7.0）。** 语义上不可推断的字段强行推断，把
   所有未识别 agent 记成 human，一个版本即废。教训：设计字段先问"它到底
   回答什么问题"。
2. **记录模型方向反复（0.2.5–0.2.6 vs 0.14.0）。** rejected 状态删了又
   回来、草稿从 `.drafts/` 变 `proposed/`、命令更名 decide→record /
   accept→implement。根因是 dogfood 之前格式设计靠想象。
3. **归档封印（ADR 19）。** manifest 与被保护文件同库同权，防不了协同
   篡改；格式漂移后归档不可修复。四周后整体拆除。教训：引入机制前先问
   Git 是否已经解决了它。
4. **ADR 27 一日游。** 为封印打补丁（归档豁免现行规则）次日连补丁带机制
   一起拆。打补丁时，"拆掉整个机制"这个更根本的选项应当同台评估。
5. **可视化层先发布后治理（0.10.0 → 0.11.0）。** Mermaid-CDN 与满屏常量
   徽章一天内分别被离线渲染和"earn the ink"取代；同日两个 minor 版本，
   同一问题拆成两次公开变更。
6. **"无用户"前提使用过界。** 该前提支撑到外部仓库已停在 0.18.1 之后
   （0.20.0 点名 article-helper），期间破坏性变更持续按 minor 发布、无
   迁移说明。ADR 28 补上了立场，但纠正晚于事实。
7. **已知威胁的防护后置。** 多 agent 并发写在 AGENTS.md 里，编号锁却等
   到 0.22.0；输入健壮性（ReDoS、FIFO/设备文件）等到 0.13.0 审计才发现。
   声明过的威胁类别应在首次实现时防护。
8. **早期品牌与命令面频繁变动。** OpenADR → ADR Kit、包名更换、核心命令
   更名，对早期采用者是纯成本；更名与破坏性格式变更同版本叠加放大了
   迁移负担。

## 给下一阶段的三条提醒

- 破坏性变更的 README 升级说明与 standing-orders 漂移提示已经就位
  （ADR 28、0.22.0），继续守住"说清破坏点 + 迁移机械部分"的底线；
  外部用户存在这件事从此不再是前提，而是事实。
- 机制类提案（新的清单、封印、索引）默认先与 Git/validate 的既有能力
  对表；ADR 19 的教训值得作为评审清单项。
- 0.9.0 的分水岭说明：任何新格式或新工作流，先在本仓库用满两个发布周期
  再向用户推广。
