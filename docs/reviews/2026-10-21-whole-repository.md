## Standards：规范、流程与文字

### S1 · P2：校验清单把“必须有标题”描述成“各节必须有内容”

位置：`docs/cli.md:65`、`docs/zh/cli.md:57`；实现为
`src/core/validate.ts:226,254`。

中英文清单称必备小节各有实际内容，实际只有 Problem、Decision/Proposal、
Alternatives considered 必须有内容。Acceptance criteria、Risks、Consequences
只要求存在标题。实测提案的 Acceptance criteria 与 Risks 仅含 HTML 注释仍通过。
ADR 21 本身也记载模板会触发三项内容缺失，不能擅自将现行规则扩大成五项。

修复：准确区分标题要求和内容要求；如果要提高门槛，另行决定并同步规则与测试。
成本低，值得修。这里的夸大表述出自本轮审查前刚提交的 `ab3ecaa`，上一轮修正文档
仍遗漏了这一点。

### S2 · P2：propose 工作流在未交付阶段要求 supersede

位置：`skills/adrkit-propose/SKILL.md:13`，生成镜像
`src/core/tool-integrations.ts:162`；standing orders 也有同类概括。

“完整替代”分支要求写完新记录就在同一变更里 supersede 旧记录。但该工作流创建的
是 unshipped proposal，而 `src/commands/supersede.ts:28` 要求 replacement 是
implemented。复现中传入合法新提案，命令明确拒绝。照做会卡住，或诱导提前晋升，
与 ADR 18 的“交付后才 implemented”冲突。提案本身不是第二份当前权威。

修复：提案阶段链接替代意图、保留旧权威；实际交付并晋升的变更里完成 supersede。
同步技能、生成镜像与概括规则，并测试这条完整流程。成本低，值得修。

## Spec：行为与承诺

### F1 · P1：归档清单部分写入失败会破坏已有封存

位置：`src/core/archive-seal.ts:125-126`，回滚边界
`src/core/retire.ts:60`。关联 ADR 19。

`writeFileSync` 先截断正式 MANIFEST.json 再写新内容。实测先归档四条记录，原清单
522 字节；将子进程 RLIMIT_FSIZE 设为 550，再归档第五条。命令因 EFBIG 失败，
第五条源记录保留、暂存归档撤回，但正式清单变为 550 字节的无效 JSON。原先四条
封存也无法继续验证，需从 Git 或外部副本恢复，不能把回滚称为完整恢复。

修复：在同目录写临时清单，写完并关闭后原子替换正式文件；失败时保留旧清单。
用真实部分写失败测试“旧清单字节不变”，不能只测写入前的权限失败。
触发频率低，但影响全部历史封存，修复局部且收益高，应优先处理。
旧评审曾将一般非原子写列为暂不修；如今 ADR 19 的持久封存与回滚承诺使这里的
后果更具体，不能继续沿用旧结论。

### F2 · P2：Markdown 注释与代码围栏的解析状态不一致

位置：`src/core/adr.ts:465-480`、`:248-252`。关联 ADR 16、25。

把全部必备章节放在一个 `<!-- ... -->` 内，validate 仍返回 OK。解析器把注释内 H2
当成章节，第一节之前的注释开头被丢弃，后续内容检查已无法知道文本不可见。
这样的空白外观记录还可能被归档封存。

另一侧，writtenHeadings 先全局去注释再处理围栏：围栏内的 HTML 示例 `<!--`
会吞掉后面可见的 `### Risks`，使 ADR 25 的规则失效。两种情况均实测。

修复：使用同时理解注释与围栏状态的线性扫描，保留原始正文；不要简单在解析前
全局删除注释。分别测试跨章节注释及代码样例中的注释标记。成本中，值得修。

### F3 · P2：合法提案晋升后变成无效记录，源提案已被删除

位置：`src/core/templates.ts:202-205,242-244`；调用边界
`src/commands/implement.ts:40-42`。关联 ADR 18、25。

合法提案允许自定义 `## Decision` 或 `## Consequences`。生成器自己创建这些章节，
又把同名自定义节原样附加。实测提案校验通过，implement 成功并删除提案，随后
校验报告 duplicate section。状态转换只检查了输入，没证明输出满足目标状态。

修复：在写入/删源前检测目标保留标题冲突，明确拒绝或合并；加入转换后结构有效的
不变量测试。不得以静默丢弃用户章节来消除重复。成本低至中，值得修。

### F4 · P2：并发 note 两者都报告成功，最后只剩一条

位置：`src/core/notes.ts:37-39`。关联 ADR 21。

appendNote 实际是读全文、拼接、覆盖写回。两个真实进程都读完再一起写，两者正常
返回，但最终 notes.md 只包含一条新 note。编号写入的锁不覆盖该独立缓冲区。

修复：使用追加写或对读改写加锁，兼顾手工文件末尾没有换行的情况；并发测试应
确认两条内容均保留，而不只是两次调用都成功。多 agent 捕获决策会触发，成本低，
值得修。

### F5 · P2：不可读取的代码让引用校验从失败变成成功

位置：`src/core/markers.ts:126-129,147-155`。关联 ADR 26；完整性原则参考 ADR 23。

bad.ts 引用不存在的 ADR 999 时 validate 失败；将其权限设为 000 后 validate 返回
OK。扫描器将 stat/read/readdir 错误当作没有内容，操作者无法区分“没引用”与
“根本没检查”。这与 ADR 26 已明确接受的大文件、二进制、依赖目录排除不同。

修复：采集失败形成明确诊断并使校验失败；保留明确声明的排除策略。成本低，值得修。

### F6 · P2：有提案时 instructions 隐藏整仓错误

位置：`src/commands/instructions.ts:39-60`；公开保证见 `docs/cli.md:108`。

完整提案与 bad.ts 的失效引用同时存在，validate 明确失败，instructions 却只显示
“validated - ready after shipping”及 implement/reject 建议。提案分支提前返回，
掩盖了已经计算出的非配置类整仓问题；封存与目录问题也落在这个分支之外。

修复：同时展示提案进度与整仓问题，不让二者互斥；对局部“ready”的措辞明确范围。
成本低，值得修。

### F7 · P2：能匹配真实文件的 glob 被漂移检查拒绝

位置：`src/core/validate.ts:122-126`、`src/core/glob.ts:68`。关联 ADR 22、23。

存在 src/cli.ts，作用域写 src/cli*.ts：relevant 正确匹配，validate 却检查不存在的
src/cli，并称“matches nothing”。wildcard 前的半个文件名不是应当存在的完整路径。

修复：明确静态目录锚点与无 wildcard 精确路径的检查规则，兼容文件名前缀与 `?`；
同时澄清 ADR 22 的静态前缀措辞，避免只改实现留下错误约束。成本低至中，值得修。

### F8 · P2：目录检索漏掉符号链接文件，却报告采集完整

位置：`src/core/relevant.ts:74`。关联 ADR 22、23。

src/linked.ts 指向 ../real.ts，记录仅作用于 src/linked.ts。直接查询文件能匹配；
查询 src 目录却没有匹配，complete 为 true，也没有诊断。Dirent.isFile 不包含符号
链接，路径在目录遍历中无声消失。

修复：把符号链接路径作为候选叶子，不必递归跟随其目标目录；或明确声明排除并给出
完整性提示。命名路径本身不要求打开目标文件。成本低，值得修。

### F9 · P2：归档清单绕过普通文件保护，可使验证无限读取

位置：`src/core/archive-seal.ts:116-120`。关联 ADR 16 的读取边界。

在初始化仓库把 MANIFEST.json 换成指向 /dev/zero 的符号链接，子进程进入 validate
后持续读取，400 ms 无结果，被测试强制终止。该符号链接可以被 Git 携带；这不需要
竞争交换文件。archive/supersede 的预检查共用同一读取器。

修复：对清单先应用普通文件检查，再读内容；保留指向普通文件的链接策略。验证应
及时报告文件种类。不能只给测试加超时掩盖运行时问题。成本低，值得修。

## 会持续产生问题的机制

1. **只校验输入，没有验证状态转换的后置条件。** F3 是直接后果；F1 表明回滚也没有
   覆盖所有已变更状态。应在现有命令与 retirement 边界增加明确不变量，不必另造
   通用事务框架。
2. **多份对“可见 Markdown”的解释。** 章节解析、内容判断、子标题检查各自处理
   不同子集，局部修补一个规则仍会留下另一条路径。F2 值得共享一段窄范围扫描器，
   不值得引入完整 Markdown 运行时依赖。
3. **未知被悄悄变成成功或完整。** F5、F6、F8 分别发生在扫描、汇总、检索，显示
   ADR 23 的完整性纪律尚未贯彻到相邻功能。明确区分“有意跳过”与“获取失败”。
4. **文字镜像相同不等于流程正确。** 技能和生成模板同步、双语键一致的测试是有效
   防线，但挡不住 S1、S2 这种两边同时错误。需要少量端到端流程与承诺测试。

## 未作为缺陷的事项

- archived 保留历史 implemented 状态、但不再是当前权威，是 ADR 18 的有意设计；
  不能仅因 folder 与 status 不同就判状态机错误。
- 同时执行多个归档清单事务目前明确不受编号锁保护，文档要求串行，本轮没有把
  已声明的限制重复包装为新问题。
- 新骨架记录未填完时 validate 失败是正确行为，不应为“全绿”而放宽门槛。
- 直接检查的 CLI 选项表、Git 参数数组与 NUL 分隔、HTML 输出转义、离线生成与共享
  交互模块没有发现同等确定性的缺陷；浏览器行为未实测，不能据此保证全无问题。
- 双语与技能镜像有维护成本，但属于仓库明确选择；没有证据支持大规模抽象或重构。
