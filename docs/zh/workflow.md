# 工作流

## 何时记录

保留现有来源未能表达的重要上下文。尊重用户明确要求保留的选择，但不将其扩展为同类改动的记录义务。

创建或整形记录前，判断三个问题：

1. **会丢什么？** 找出代码、测试和现有文档无法可靠解释的约束、理由或真实取舍，尤其是会话独有的上下文。实现结果本身不够。
2. **丢了怎样？** 指出可能的误改及其后果，综合重要性和影响面判断；局部但后果严重的选择也可记录。不能为记录编造灾难。
3. **留下什么？** 保留稳定的选择、边界和理由。分别考虑长期性与不易腐烂，易变事实交给代码、配置、测试或已有文档。

凭判断，不打分，也不要求各项全过。没有有意义的信息会丢失，就跳过，无需证明字段、用户批准或留 note。note 是候选，不是必须写 ADR 的承诺。

| 通常交给现有来源 | 可能值得保留 |
| --- | --- |
| 升级 adr-kit 到某版本，Git 和锁文件已有事件记录 | 用户只在会话里说部署环境无法访问公网，这会约束后续依赖与升级 |
| 调整按钮间距或阴影，样式和视觉检查已有结果 | 稳定的可访问性约束限制后续视觉调整，背后理由不易察觉 |
| 选用了某个库，依赖清单已经表达结果 | 部署限制解释了为何另一个看似更合适的库或运行机制不可用 |

判断信息而非领域名词；已有记录不构成记录同类改动的先例。只更新因改动失真的实际陈述，保持必需路径和引用有效。易变细节造成反复同步时，指出负担，建议将细节交回已有来源，或在理由不再指导工作时经授权归档。不能悄悄改写选择、忽略约束、删除记录或未经授权归档。

Grilling 使用同一判断标准，讨论过不代表必须记录。存在值得记录的结果时，完整
会话树保存在该记录的 Deliberation 附录，局部答案作为背景，不成为独立维护义务。
没有值得记录的结果时，在会话中总结，不创建记录。讨论定向不等于实际交付。

可用[记录判断场景集](../recording-evaluation.md)验收 agent 行为。它是人工评估协议；
模板测试通过不代表模型质量已获验证。

## 生命周期

1. `adrkit propose "<标题>"` 在 `proposed/` 创建未编号提案，可编辑并提交
   Git 供审阅。方向已定但尚未交付仍留在这里。
2. 交付后运行 `adrkit implement <name> --raised-by <human|agent>
   --decided-by <human|agent>`，校验并移入编号的 `implemented/`。未经过
   提案但已交付的选择，用相同来源声明运行 `adrkit record <title>`。
3. `adrkit reject <name> --reason "<它挡住的诱惑性错误>"` 把否决提案记为
   `rejected/` 的稳定反例终态，不分配 ADR 编号。保留它；只有当另一条记录
   接管了它挡住的错误时才移除，绝不因「看起来过时」而删。否决记录没有编号，
   因此移除一条多余的否决不会腾出可复用的编号。
4. 完整替代用 `adrkit supersede <old> --by <new>`：旧编号记录带
   `superseded-by` 进入 `archived/`。部分替代仍保留有效的现行指导。
   其他低未来价值记录，仅当现状另有权威来源时，才用 `adrkit archive <N>
   --reason "<现状来源>"` 归档；绝不按年龄归档。两条命令都把最终记录移入
   `archived/`，后续变化由 Git 记录。只要代码仍在引用该记录，两条命令都会拒绝
   执行并列出每个 `path:line`：此时移动会让 `validate` 否决的引用悬空，先改写或
   删除这些引用。`supersede` 还会拒绝编号小于被替代记录的 `--by` 决策。
5. `adrkit validate` 检查四个目录，包括归档记录。新模板必填章节未填时会失败。
   `adrkit atlas` 写出可浏览的决策档案，`adrkit atlas --record <name>`
   绘制可选 `## Deliberation` 附录的 deliberation tree。

`adrkit-visualize` 技能还附有可选的档案页示例，位于安装后的技能目录内
`examples/decision-atlas.html`。需要更完整的浏览体验时才参考它，按目标仓库
实际数据裁剪章节；少量记录仍可用列表或内置决策地图。示例是参考快照，不是新的
CLI 输出格式，也不是必用布局。

## 让记录与已交付代码保持一致

创建、交付、审查构成同一个治理闭环：

- **创建前**：在现行记录中检索涉及同一选择或机制的记录，依据内容而非标题
  判断重叠。重复则扩写原记录；未交付的完整替代先链接替代意图，
  保留旧决策的现行权威，等替代方案交付后，在同次交付变更中用
  `adrkit supersede --by` 解析旧决策；部分替代则链接两条记录，旧记录保持现行。
- **交付时**：将记录声称的路径、名称、默认值、机制与当前代码和测试核对，
  用已交付的事实替换提案期的意图。如果代码改动只改变了某条现行决策的实现
  事实，只更新原记录实际声称的内容；实现自由范围内的变化无需同步。被记录的
  选择本身变了则必须另立记录并写明关系。
- **代码实现某条决策时**：在注释里用 `@adr <编号>`（如 `@adr 14, 22`）引用
  它。引用可选；指向不存在、已归档或已替代的决策，或引用文件不在该记录的
  `paths` 内时，`adrkit validate --all` 会失败。
- **审查时**：`adrkit-review` 工作流将变更记录与变更代码对照，检索过时的
  实现事实和未解析的替代关系，并给出有证据的结论。它只关注决策记录的
  一致性，不是通用代码审查；没有发现也是有效结论。

## 任务开始前阅读决策

任务开始先运行 `adrkit list` 发现目录清单。四个目录是一份上下文预算：
完整阅读相关 `implemented/` 记录；检查相关 `proposed/` 的意图与
`rejected/` 的反例；`archived/` 是冻结历史，仅当任务明确引用时再读。不能
只看标题判断相关性，还应看描述、路径、关系和任务范围；任务涉及具体文件时，
`adrkit relevant <path>` 检索通过 `paths:` 限定管辖它们的记录。将记录与当前代码核对，
解释假设变化，在总结中提及相关 ADR 编号。任务范围变化后重新阅读。
Agent 技能指导生命周期操作，但 CLI 不会自动编辑 `AGENTS.md`。


## 用证据共同设计

开工前先用 `list`、`relevant <计划路径>...`，再通过 `show` 完整阅读相关现行
记录、提案和反例。探索时分清仍适用的约束、变化的假设和冲突。代码观察引用已读的
file:line 或符号，外部事实带来源链接，参与者陈述注明归属。区分观察、推断与未知；
实现代码本身不能解释某个替代方案为何落选。不能为了填模板编造理由或备选。
证据写在现有章节的普通 Markdown 中，不新增必填字段。

note 可在同一行附已有来源，例如：`Candidate: use SQLite; rationale unknown;
source: PR #42`。来源可选，捕获仍只需一行；候选不等于定案，note 不证明交付或
决策来源。整形前核对来源；材料被截断或会话与变更时段不对应，要明示限制，不能
悄悄绑定。未知理由需澄清后才能作为已定事实。

审查时根据实际修改重新检索：`adrkit relevant --base <review-base>` 直接比较
指定提交到工作区，含未忽略的未跟踪文件；`adrkit relevant --staged` 只看暂存区。
删除和重命名保留旧路径。范围命中仍需结合目录清单，解决不完整搜索的诊断并完整
阅读命中记录；零命中不是忽略约束的许可。校验通过证明记录有效，代码是否遵循
决策仍需单独审查和对应的测试证据。
